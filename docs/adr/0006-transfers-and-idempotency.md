# ADR 0006: Transfers with idempotency keys and ordered row locks

**Status:** accepted (Milestone 4)

## Context
Mobile clients retry. A response lost after commit must not cause a second transfer. Concurrent transfers must not overdraw accounts or deadlock.

## Decision
- **Idempotency key per user intent**, generated by the client and reused on every retry. Stored on the `transfers` row with `UNIQUE (user_id, idempotency_key)` plus a SHA-256 of the canonical request.
  - Same key + same request → the original result with `replayed: true`. Nothing moves.
  - Same key + different request → `IDEMPOTENCY_KEY_REUSED`.
  - Failed requests leave no row (the transaction rolled back), so a retry re-evaluates. Safe, because nothing moved.
- **Transaction flow (READ COMMITTED):**
  1. Fast path: look up the key outside any transaction.
  2. Lock both accounts in one statement: `SELECT … WHERE id IN (a, b) ORDER BY id FOR UPDATE`. A global lock order makes A→B / B→A deadlocks impossible.
  3. Validate ownership, recipient, currency and balance under the lock.
  4. Insert the `transfers` row (the idempotency claim) and post the ledger transaction. The FK to the ledger transaction is deferred to COMMIT, because the transfer row is written first with an id the app generates (UUIDv7).
- **Duplicate race:** a losing duplicate fails either on the unique index (P2002) or with `INSUFFICIENT_FUNDS` (it saw the winner's debit after waiting for the lock). In both cases the service looks the key up again and returns the winner's result.
- **Deadlock/serialization retry:** `40P01`/`40001` are retried up to 3 times with jittered backoff. That's safe only because the whole operation is idempotent.
- **Audit:** `transfers` is append-only (trigger) and records the initiator, the request hash, and the correlation id (HTTP request id).
- **Simulated deposits** use the same path from a system `external-funding:<currency>` account. They are labelled `SIMULATED_DEPOSIT` in the API and capped at 50,000.00 per operation.

## Alternatives considered
- **SERIALIZABLE isolation instead of explicit locks.** Correct, but turns every conflict into an abort-and-retry. Ordered `FOR UPDATE` is cheaper for a known contention pattern.
- **Optimistic concurrency (version column).** Same retry cost under contention; the hot path here is contended by design (a busy account).
- **Idempotency in Redis.** Not durable and not atomic with the ledger write. The key must commit in the same transaction as the money.
- **Storing failed attempts under the key** (Stripe-style). Gives retries a stable error, but would freeze a retry after the user tops up. Not needed while failures move nothing.

## Consequences
- Verified by mutation tests: with unordered locks, 20 opposing transfers produced 24 deadlock retries and still failed. With ordered locks there were zero retries.
- The client must keep the key for the life of the user's intent (e.g. until it sees a result) and must not reuse it for a new intent.
- Single-account throughput is bounded by the row lock. Acceptable for retail banking.
